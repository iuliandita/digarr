# Changelog

All notable user-facing changes are documented here.

Releases that have been promoted to the `:stable` Docker channel carry a `(stable)` marker after the version heading. Promotion happens after a release has been live for at least seven days with no follow-up patch.

## Unreleased

### Added

- Built-in Streamable HTTP MCP endpoint at `/api/v1/mcp` for recommendations, approvals, rejections, blocks, scans, discovery modes, job status, artist search, and playlists. Personal API tokens are required; read scope permits read tools only. Account settings shows a copyable client configuration after token creation in all 15 languages. No extra service or MCP session store is needed. (#979)
- slskd targets now let you set a minimum search gap (3 seconds by default, 1-60 seconds) and keep jobs retryable with bounded backoff when slskd returns HTTP 409/429 (#971).
- The slskd connection test checks the linked Lidarr download directory, reports missing or unlistable paths and likely incomplete folders, and shows the result in your language (#972).
- Personal API tokens in Settings > Account for scripts and automation, with read, write, or admin scope, optional expiry, one-time reveal, last-used metadata, and immediate revocation. Stored as SHA-256 hashes only and excluded from application backups and backend copies. Recreate tokens after recovery onto a fresh instance; password changes and logout keep them active, so revoke them if a password was compromised. Read/write tokens never inherit admin access, and exhausted failed-auth budgets block credential lookups. Legacy `DIGARR_AUTH_TOKEN` keeps working with a startup deprecation pointing at personal tokens. Migration 0057 adds a table; take a complete backup before upgrading. Rolling back leaves it unused and tokens stop working on older images; existing sessions remain supported. (#978)

- Get an artist's missing studio albums in one step from a recommendation's details, a Gap-Fill result, or an approved artist. Review the count, untick albums, and approve the rest together. The same Gap-Fill selection and single-album Lidarr monitoring apply, with per-album failures shown for retry (#976).

- Lidarr approvals and auto-approval now offer missing, existing, latest and first-album monitoring. Each Lidarr target can set default tags, with per-approval overrides and tag creation from its own instance. Tags also apply when an album approval adds a missing artist (#974) (#975).

- Helm: `networkPolicy.extraEgress` (empty by default) appends your own egress rules, for an external database, Lidarr, a local AI server, or a media server on a private network. The install notes now warn when `postgresql.enabled=false` runs with the default NetworkPolicy, or when no `ALLOWED_ORIGIN` is set behind an Ingress or Gateway. Documented `image.digest: null` to float a tag (#911).
- Documented the PostgreSQL 15 or newer requirement for an external database in the README and the Docker, Helm, and Synology guides (#911).
- Maintainer docs: `docs/NORMALIZATION.md` lists every stored normalized artist and album key and the migration, collision, and backup-restore plan for changing a normalizer. A contract test pins the current outputs so a rule can't change by accident (#920).

- Import artists from M3U, M3U8 and XSPF playlist files in the same import section as CSV. Artists come from `#EXTINF` lines and XSPF `creator` tags. A path-only M3U entry counts only when it reads `Artist/Album/NN - Title` or a flat `Artist - Title`; anything else is skipped and reported as "N entries couldn't be read" after the import instead of guessed. Duplicates are merged, and the existing 1 MB and 500-artist limits apply (#981).

The `-debian` image is built (not pushed) on pull requests that touch `deploy/docker/`. ### Fixed
- MCP requests now accept single messages only and enforce a 1 MiB body limit. Scan-start rate limits apply only to MCP tools, preserving REST scan behavior. Client configuration includes the HTTP transport type. (#979)
- Rate limits behind a trusted reverse proxy now use the real client IP, so one client cannot exhaust every client's login budget. Configure `PROXY_AUTH_TRUSTED_PROXIES`; untrusted peers still use their socket IP. Limits and windows are unchanged (#1008).
- Lidarr is configured in one place again. Lidarr targets now point at the Lidarr connection in Settings > Connections instead of keeping their own copy of the URL and key, so changing the connection reaches approvals right away. The default quality profile, metadata profile and root folder moved into the Lidarr card. A target for another Lidarr instance stays possible under "Use a different Lidarr instance", with its own profile and folder defaults loaded from that instance; it no longer gets the main instance's IDs. The approve dialog shows monitoring up front and the profile pickers under a collapsed "Lidarr options", loaded from the target actually used, and `GET /api/v1/lidarr/approve-options` accepts `?targetId=` and returns the effective defaults. On upgrade, targets matching the connection's URL and key are linked automatically; see the OPERATIONS upgrade note for other targets and rollback (#994).
- slskd now auto-queues a release that several peers share instead of sending it to manual review. Identical releases from different peers are no longer treated as ambiguous; the peer is picked by free upload slot, then shorter queue, then faster upload speed (#969).
- slskd no longer re-searches and re-downloads a failed release every hour forever. Automatic retries from the Lidarr wanted list stop after three retries (waits of 1 hour, 6 hours, then 24 hours) and the job stays failed until you approve it again, which resets the count. A retry skips the peer and folder that already failed, and the job error shows the attempt number (#970).
- Green, blue and amber status text (approve, info, warning) and the filled Approve button now reach the 4.5:1 contrast minimum in every color theme, including on the tinted badge and notice backgrounds; most light themes were well below it. Each color moved only in lightness, so the hue is unchanged (#966).

- The Playlists page header now describes the page instead of repeating the schedule status; the next generation time now shows in the Scheduled generation row, and the lint run is clean again after removing an unused admin check from the Dashboard. (#954, #957, #962)
- Library reconciliation now matches an artist stored under a MusicBrainz alias or sort name, such as 아이유, 방탄소년단 or 블랙핑크, instead of leaving it without a candidate. Matching is still exact after normalization, a match on the primary name wins over an alias match, and several alias matches still count as ambiguous (#958).
- Every theme now reaches 4.5:1 for text, muted text, button text, links and red text on the surfaces they sit on. Muted text is lighter in dark themes and darker in light themes, red text is adjusted where it was too faint, links get their own shade where the theme's accent was too dark or too light to read, and a few light themes use a slightly deeper accent behind white button text. Spotarr, light Tidarr and dark Qobuzarr buttons now use dark text on the accent, and dark Deezarr and Applarr buttons darken on hover instead of lightening. Hues stay the same, so each palette keeps its look. A test now checks every theme so a token change can't drop below the minimum unnoticed (#953).

The release-group lookup now asks MusicBrainz for aliases in the same requests, the same exact-match, primary-title-first and ambiguity rules as artists apply, and `GET /api/v1/albums/:mbid` returns an optional `aliases` list (#964).

Other themes look the same. Page tips use the info color instead of the accent, so they no longer read like errors in red themes. Health's "Building your library catalog" banner only shows while a first library sync is actually running, not when no library source is configured. Setup's Lidarr step asks for the API key before the Advanced section, Reconciliation hides "Select visible" when a list is empty, phone bottom-bar labels such as "Subscriptions" fit at 390px, the Discover toolbar divider lines up with the content, and the Dashboard's Recently Approved and Listening History cards match heights (#951).

### Fixed

- **Large Lidarr libraries no longer fail to sync with an unexplained "The operation was aborted."** Lidarr returns the whole artist list in one response and offers no pagination, so a large library can take well over a minute to serialize -- one report measured ~54 MB and ~83 seconds for 7100 artists. Digarr allowed 10 seconds and then retried three times, so the sync died after ~43 seconds having asked Lidarr to serialize the entire library four times over. The full-library fetch now gets 120 seconds and no retries, tunable with `DIGARR_LIDARR_TIMEOUT_SECONDS`; every other Lidarr call keeps its short timeout so an unreachable Lidarr still fails fast. Timeouts now report the budget that elapsed instead of a bare abort, and the library fetch names the environment variable to raise. Separately, approving an album no longer downloads the entire artist list just to check whether the artist is already tracked -- it asks Lidarr for that one artist -- which is why approvals could fail on large libraries even when the scan was not running. Reported in [#589](https://github.com/iuliandita/digarr/issues/589).
- **A discovery mode whose streaming connection has gone stale now says so, instead of claiming you never connected.** Spotify, Deezer, and TIDAL discovery modes reported every failure -- an expired token that could not be refreshed, an encryption-key mismatch, a database error -- as "Connect <provider> to use this mode.", even while Settings still showed the provider as connected. Those cases now say the connection is no longer usable and to reconnect, and the underlying error is logged instead of being discarded. A genuinely missing connection still reads as before.
- **TIDAL token refresh now authenticates the same way the initial connect does.** The authorization-code exchange sends HTTP Basic credentials while the refresh sent them in the form body. Only one of the two can be right for a given TIDAL app, and a mismatch would have surfaced as an unexplained disconnect roughly an hour after connecting. Refresh now mirrors the exchange. Relevant to the unvalidated TIDAL flow tracked in [#553](https://github.com/iuliandita/digarr/issues/553).
- **Spotify and Deezer connect failures now report the same detail TIDAL already did.** A token endpoint that could not be reached, or that answered without an `access_token`, previously surfaced as a generic failure (or, for an unreachable Spotify endpoint, a server error page). All three providers now map to the same `oauth_error` stages, and the upstream error body is logged secret-redacted.
- **Credential redaction now catches `client_secret=` and `refresh_token=`.** The redactor keyed on a word boundary, which snake_cased parameter names slip past, so those two could reach logs unredacted.
- **A failed login over plain HTTP now says which setting to change.** Signing in from another machine on a direct-HTTP install failed with "The browser did not accept the session cookie", which named the symptom but not the fix. The cause is that session cookies are `Secure` in production and browsers keep those only over HTTPS and on `http://localhost` -- so logging in works on the machine running Digarr and fails everywhere else. When the page is served over plain HTTP from a non-localhost address, the login screen now explains that and names both remedies (serve over HTTPS, or set `DIGARR_ALLOW_INSECURE_COOKIES=true` with a matching `ALLOWED_ORIGIN`). A production instance in that configuration also logs a warning at startup, before anyone reaches a login screen, and `docs/AUTHENTICATION.md` gained a troubleshooting entry under the error text. Translated across all 15 shipped locales.

## v1.15.0 - 2026-07-29

### Security

- **Provider OAuth connect flows are hardened, and starting one no longer risks your existing connection.** In-flight Spotify, Deezer, and TIDAL authorizations moved out of the stored-token row into their own table, so abandoning a re-connect leaves the working connection untouched (previously it was replaced by a pending marker and the provider went silently disconnected). The one-time `state` is now stored only as a SHA-256 digest, its 10-minute expiry is enforced instead of merely recorded, and the row is deleted the moment the state is redeemed, so an abandoned or failed flow can no longer leave a redeemable state behind. Starting a connect also sets a short-lived `HttpOnly` transaction cookie, mirroring the OIDC login flow: the callback must arrive from the browser that started it, which closes an account-injection path where someone holding a leaked `state` could bind their own streaming account to another user's Digarr account. Note for TIDAL: with `ALLOWED_ORIGIN` unset, the browser-supplied callback URI is now accepted only outside production and only for a loopback host -- production installs must set `ALLOWED_ORIGIN` to connect TIDAL. - **Webhook notification URLs are now encrypted at rest and masked in the settings API.** Discord and Slack webhook URLs carry their secret in the URL path, so they now get the same protection as the other channel secrets: field-encrypted in the database, and returned partially masked by the settings API (the host and path structure stay visible so you can recognize the destination, while the secret tail and any query-string values become `***`). Leaving the masked value untouched on save keeps the stored URL; entering a new URL replaces it. Existing webhook URLs are encrypted on their next save.

- **Session cookies now fail closed to `Secure` in production.** Production session and OIDC transaction cookies are marked `Secure` even when the backend request arrives over HTTP, so a TLS-terminating reverse proxy no longer emits plaintext-eligible cookies. TLS termination requires `ALLOWED_ORIGIN=https://public-host` for correct CSRF and public-URL behavior. Direct production over HTTP needs the explicit `DIGARR_ALLOW_INSECURE_COOKIES=true` opt-in (default `false`) and remains vulnerable to network interception; pair it with a matching `http://` `ALLOWED_ORIGIN`.
- **OIDC login state is now browser-bound and single-use.** The authorization state lives in a state-scoped `HttpOnly` transaction cookie, is consumed on the callback, expires after 10 minutes, and is safe across multiple concurrent tabs. - **Password change and session replacement are now one atomic transaction.** The change verifies the stored password hash and replaces every session under a single user-row lock, so a password verified before a concurrent reset can no longer mint a post-reset session.

- **Browser sessions now stay in HttpOnly cookies instead of JavaScript storage.** Web password and registration flows, OIDC, and trusted-proxy sign-ins use `SameSite=Lax` cookies. Production session and OIDC transaction cookies default to `Secure` even when the backend request arrives over HTTP (for example behind a TLS-terminating proxy); direct-HTTP production must opt in with `DIGARR_ALLOW_INSECURE_COOKIES=true`, which drops `Secure` only when the public origin is `http:`. State-changing browser requests now require same-origin evidence plus a CSRF header. Existing per-user browser bearer sessions are rotated once into cookies and removed from storage; OIDC no longer hands a session token through the URL. Bearer login remains supported for API clients, and query-token compatibility remains limited to pipeline SSE and preview audio.

The unused token table, backup and backend-copy paths, and encryption-rotation coverage are removed. Restoring a legacy backup ignores an empty `oidcTokens` table and skips nonempty rows with a warning. A binary downgrade requires stopping Digarr, provisioning a fresh old-schema database, and restoring a prepared compatibility copy of the pre-migration backup; an older image must never run against the migrated database.

## v0.28.5 - 2026-04-17

Security-critical release: closes the three-step unauthenticated admin-takeover chain identified in the deep audit, plus surrounding auth-surface hardening. All authenticated users should keep working without action; the tightenings only affect new registrations and newly-rotated passwords.

### Fixed

- CIDR matching now supports IPv6 with a strict parser. The prior IPv4-only implementation silently passed IPv6 addresses through an integer-only check, allowing an IPv6 address like `2400:beef::1` to match an unrelated `2400:cb00::/32` CIDR and bypass proxy-auth trust boundaries. The new parser validates each family independently and rejects leading-zero octets (CVE-2021-29923 class).
- `PROXY_AUTH_TRUSTED_PROXIES` entries are validated at boot. Unbounded ranges (`0.0.0.0/0`, `::/0`, plus every textual variant that normalizes to `/0`) are refused so a misconfigured deployment fails loudly instead of silently trusting the internet.

Proxy-auth previously reused any active session for the resolved user, which could hand a password-mode session's raw token back via `/api/auth/status` when the same user had also signed in through the proxy. - `/api/auth/status` no longer echoes session tokens to the client. Authenticated callers rely on the cookie for follow-up requests; the response exposes `authenticated`, `userId`, and `isAdmin` instead.

Two concurrent setup or registration requests can no longer both succeed as admin; the losing request is resolved to the existing admin or retried as a non-admin. The migration auto-demotes extra admins (keeping the oldest) with a `RAISE NOTICE` when applied against a database that previously accumulated duplicates.
- OIDC callbacks sanitize the `preferred_username` claim (allowlist `[A-Za-z0-9._-]`, 50-char cap) so an untrusted IdP cannot inject arbitrary characters into usernames that flow into filesystem, SQL, or UI contexts.

- Auth middleware returns `503 re-run setup` for the degenerate state where setup is flagged complete but no users exist (orphaned DB state). Callers no longer retry against a dead deployment indefinitely.

- OIDC email-verified auto-link is now opt-in. A new `OIDC_TRUST_EMAIL_VERIFIED` environment variable (default `false`) must be set to `true` before an OIDC sign-in will automatically link to an existing local account on matching `email_verified=true` claim. `docs/AUTHENTICATION.md` documents the threat model (single-tenant IdPs safe to enable, public issuers not).
